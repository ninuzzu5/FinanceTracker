Snapshot: branch `dev`, HEAD `380cf9a`, working tree inizialmente pulito.
Codice applicativo e migrazioni non modificati. Sono stati aggiunti solo test,

## Valutazione

Le riconciliazioni hanno retto i casi concorrenti provati e l'isolamento tra utenti
è rispettato nelle migrazioni locali. I normali salvataggi non hanno però la stessa
idempotenza. Prima di utilizzare denaro reale, correggerei almeno duplicazioni e
validazione delle nuove scritture. Nessun difetto di gravità critica è stato
riprodotto; questo audit non certifica l'assenza di vulnerabilità.

## Test e risultati

- `npm test`: 436 test superati, 252 bot + 184 dominio; 16 nuovi test di audit.
- Typecheck e build: superati senza errori.
- PostgreSQL in memoria: 31 asserzioni saldi eseguite prima/dopo 005, 50
  riconciliazione/RLS e 23 nuove asserzioni di integrità. Fixture annullate con rollback.
- PostgreSQL nativo temporaneo, solo socket locale: gli stessi test SQL, cinque
  scenari con attesa reale del lock e rifiuto di REPEATABLE READ.
- Stress: 25 sessioni operative concorrenti, 12 giornate di gara tra rettifica e
  trasferimenti, 383 tentativi nell'ultima esecuzione (385 nella precedente;
  varia il numero di nuove anteprime richieste dopo conflitti legittimi).
- 10.000 ulteriori movimenti bancari a centesimi compensati e 25 letture concorrenti:
  totale invariato. Inserimento + letture: 117 ms locali, non un benchmark Supabase.
- Parser: 1.000 importi in centesimi, 200 importi con precisione incompatibile e
  200 negativi ordinari, oltre a date impossibili, ambiguità e alias equivalenti.

**I nuovi test di caratterizzazione dei bug passano perché verificano il difetto
attuale. Non sono una prova che quei difetti siano risolti.** Alla correzione, le
relative aspettative dovranno essere invertite verso il comportamento sicuro.

Copertura positiva: centesimi, aperture assenti/prima dell'apertura, trasferimenti
nei due sensi/conti uguali, patrimonio, pulsanti obsoleti, scadenza, doppia conferma
nello stesso processo, request_id con dati identici o incompatibili, anteprime
obsolete, giornata chiusa, riferimenti OLD/NEW, cancellazione multipla atomica,
rollback, accesso anonimo/JWT assente, utenti distinti e scritture dirette negate
sulle rettifiche. RLS, trigger e vincoli sono sempre rimasti attivi.

## Rischi plausibili, non dimostrati come incidenti

- **Media:** webhook distribuiti/cold start perdono lo store e la coda in memoria.
  Il workflow locale supportato ha un processo unico; non sono stati provati veri
  deployment multiistanza né i timeout/retry HTTP di Telegram/PostgREST.
- **Media, configurazione:** APP_TIMEZONE è configurabile per i movimenti, mentre
  la riconciliazione usa sempre Europe/Rome. Con un altro fuso le date relative
  possono divergere vicino alla mezzanotte. Il fuso predefinito non ha questo problema.
- **Media, dashboard futura:** get_account_balances restituisce numeric; una
  futura somma JavaScript in Number può perdere centesimi con valori grandi o
  interpretare NULL come zero. Le RPC Contanti attuali usano stringhe/BigInt.
- **Bassa/Media, crescita:** il carico locale da 10.000 righe è passato, ma non
  dimostra latenza/SLO su milioni di righe o lunghe transazioni in ambiente remoto.
  Le query dei movimenti non hanno indici specifici per proprietario/data/conto.

## Priorità

1. B1: idempotenza durevole dei movimenti e recupero degli esiti incerti.
2. B2/B3: guardie SQL per nuove scritture, date e valute, preservando lo storico.
3. B6: lifecycle delle fonti e invalidazione delle anteprime.
4. B4/B5: parser conservativo per segni e conti ambigui.
5. Prima della dashboard: fissare il fuso contabile e il contratto monetario delle
   letture; poi validare con un progetto Supabase di test autorizzato e separato.

## Ripetibilità e limiti

```sh
npm test
npm run typecheck
npm run build
node supabase/tests/run-account-balances.mjs /private/tmp/financetracker-sql-runtime/node_modules/@electric-sql/pglite/dist/index.js
node supabase/tests/run-cash-concurrency.mjs /private/tmp/financetracker-concurrency-runtime/node_modules/embedded-postgres/dist/index.js --audit
```

I runtime sono esterni al progetto, in directory temporanee; vedere la guida
Supabase per installarli. Il secondo runner crea ed elimina un proprio cluster;
non accetta URL remoti. Sul sistema corrente ha richiesto autorizzazione fuori
sandbox per la memoria condivisa di PostgreSQL. Tutti i test sono stati eseguibili
localmente; nessun test SQL ha richiesto di disabilitare protezioni.

Non eseguiti: catalogo/policy/grants effettivamente installati su Supabase remoto,
Auth/JWT reali, rete/timeout HTTP reali, cold start distribuiti, fault di disco o
arresto forzato del processo PostgreSQL. L'Auth locale riproduce il contratto minimo
uid/ruoli; non certifica la configurazione Auth del progetto. La perdita della
risposta è simulata nei test SDK e verificata contro l'idempotenza SQL con replay
post-commit; non abbiamo indotto un'interruzione di rete nel servizio remoto.
